# Migrating existing WEB projects

> **Applies to:** Community and commercial projects upgrading to the current 6.3.43 behavior.
> **Reference baseline:** reviewed 2026-09-16. These migrations accumulated before this baseline; this is not a claim that each change first shipped in 6.3.43.

Keep a copy of your project before changing its manifest. Preserve document IDs,
unknown manifest fields and related files. Test with the target viewer version
before replacing an existing deployment.

| Older assumption | Current contract | Action |
|---|---|---|
| A GLB in `public/models/` appears automatically | Project contents come from `documents[]` | Import through the app or declare a project-relative document path |
| The source demo manifest is `public/project.json` | The source demo is `public/demo-realvirtual/project.json` | Move demo-specific references; do not rewrite legitimate customer root manifests |
| No manifest produces a synthetic demo project | Missing/invalid project manifests are load failures | Serve a valid manifest and its files; inspect Network/console errors |
| Folder name determines model/scene/library type | One document catalogue; folders organize files | Preserve document identities and use the current classification/settings fields |
| Separate legacy manifest arrays are the current format | Current schema is version 2 with `documents[]` | Open through the supported migration/read path, save and verify; retain a backup |
| A model filename or exported `models[]` binds project code | `documents[].scriptRef` explicitly binds a module | Bind the document's PLUGIN slot; compile and ship its `.js` sibling |
| Every project needs a collecting `plugins/index.ts` | A document can reference one plugin file directly | Prefer a direct file; an existing index can remain if it is explicitly referenced |
| `?scene=` is the preferred link | `?doc=` is current; `?scene=` remains a compatibility alias | Use the link generated by the current app; preserve existing IDs |
| Draft bodies live in a localStorage op log | Current autosave bodies use project storage/OPFS | Do not build recovery tools around retired draft keys; export/save before clearing data |
| User toggle equals mode exit/model clear | Separate `onActivate`/`onDeactivate` hooks | Implement synchronous, idempotent cleanup and cancel asynchronous work |
| `model-loaded` authorizes executable model logic | `model-logic-activated` reflects signature gating | Bind executable behavior at the appropriate activation event |

## Retired storage details

The former `rv-scenes/draft/<base>` and `rv-scenes/scene-draft/<id>` operation-log
keys are no longer current draft writers/readers. Cleanup code may still remove
them. Historical migration descriptions in [Persistence](doc-persistence.md) are
for diagnosing older data, not instructions for new integrations.

## Verify an upgrade

Open and save a copied project, reload it, and compare geometry, signal bindings,
library placements and project code. Exercise code consent, switching documents,
user plugin toggles and cleanup. Confirm PDF/model/script requests at the deployed
URL as well as in development. Keep the old build and matching project backup
together for rollback; do not assume an older viewer understands new features.

See [Projects](doc-projects.md), [Events](doc-events-and-hooks.md) and the
[project example](doc-project-plugin-example.md).
